# 客堂管理系统当前产品需求基线

本文是当前开发基线，用来统一「已经确定要做什么、哪些旧前提已经变更、哪些需求暂不做」。

## 1. 产品定位

客堂管理系统是面向寺院客堂的轻量在线住宿管理系统。

正式形态：部署在 Cloudflare 上，由寺院内部人员使用账号登录，管理房态、挂单、预约、用斋、营期、报表与备份。

保留形态：本地版仅作为开发、演示、灾备和离线恢复工具，不再作为日常多人协同入口。

## 2. 当前技术形态

- 前端：原生 HTML/CSS/JS，无构建链。
- 正式部署：Cloudflare Pages。
- 后端：Cloudflare Pages Functions。
- 在线数据库：Cloudflare D1。
- 后续备份存储：Cloudflare R2。
- 本地后备：sql.js + IndexedDB + `ketang.db`。

## 3. 已变更的早期前提

以下早期约束不再作为正式线上形态的目标：

- 「无服务器」：正式线上版已有 Cloudflare Functions + D1 后端。
- 「数据只在本机」：正式线上版以 D1 为权威数据源。
- 「只靠 `ketang.db` 备份」：在线版以 JSON/D1/R2 备份为主，本地 `ketang.db` 为灾备工具。
- 「本地文件夹是正式分发形态」：本地文件夹只保留开发、演示与灾备价值。

仍然保留的约束：

- 不做全寺 ERP。
- 不引入 React/Vue/Vite/Webpack 等构建体系。
- 不做 Electron/Tauri/App Store/微软商店安装包。
- 保持寺院客堂语义，面向非 IT 人员。
- 用户可见文案使用中文。
- 输入进入 `innerHTML` 前必须转义。

## 4. 用户与权限

### 4.1 内部账号

- 后台账号只给寺院内部人员。
- 不开放后台自助注册。
- 管理员创建、修改、停用账号。
- 默认角色：
  - `admin`：系统设置、用户管理、房间床位、备份恢复、全部业务。
  - `zhike`：日常住宿、预约、房态、用斋、房务、报表、历史查询。

### 4.2 外部人员

- 外部人员不能进入后台。
- 外部人员只可通过公开预约入口提交申请。
- 公开预约不能暴露房态、床位、住客、报表、用户等后台数据。

### 4.3 登录安全

- 正式公网入口可直接访问系统登录页。
- 默认账号密码只允许首次初始化/测试使用。
- 上线后必须立即修改 `admin` 和 `zhike` 默认密码。
- Cloudflare Access 不作为默认测试访问方式；如需内部强保护，可后续单独配置。

## 5. 核心业务范围

### 5.1 房态看板

看板需要显示：

- 总床位。
- 已住床位。
- 空床。
- 在住人数。
- 脏房。
- 今日预约。
- 今日到离。
- 寮别余床。
- 今日用斋。
- 运营提醒。

正式统计不应纳入备用床、备用房。

### 5.2 住宿办理

住宿办理分为：

- 现场入住。
- 提前预约。

现场入住字段包括：

- 姓名 / 法名。
- 性别。
- 手机号。
- 身份证号，必填。
- 入住日期。
- 预计离寺日期。
- 床位。
- 身份。
- 班级 / 分组。
- 来源。
- 备注。
- 押金 / 房费 / 收款方式。
- 默认用斋。

### 5.3 在住挂单

在住挂单需支持：

- 搜索。
- 编辑。
- 续住。
- 换床。
- 用斋。
- 退房。
- 删除误登记。
- 打印凭证。

### 5.4 房间与床位

房间字段至少包括：

- 房间名。
- 位置。
- 楼层。
- 寮房类型：男寮、女寮、不限。
- 备注。

床位状态至少包括：

- 可用。
- 占用。
- 维修。
- 备用。

床位分配必须排除：

- 已占用床。
- 维修床。
- 备用床。
- 脏房或不可入住房务状态。
- 性别与寮房不匹配床位。

### 5.5 用斋

用斋统计口径：

- 当日在寺挂单。
- 当日待入住预约。
- 预约转入住后不能重复计数。

每位住客支持：

- 默认早斋。
- 默认午斋。
- 默认药石。
- 按日跳过某餐。

报表需支持：

- 按日期汇总。
- 按身份汇总。
- 按房间汇总。
- 不用斋名单。
- CSV 导出。

### 5.6 预约

后台预约支持：

- 预约。
- 确认。
- 转入住。
- 取消。
- No-show。

预约可不立即分床。

预约字段包括：

- 姓名 / 法名。
- 性别。
- 手机号。
- 身份证。
- 预计入住。
- 预计离寺。
- 营期。
- 班级。
- 身份。
- 房间偏好。
- 来源。
- 用斋需求。
- 备注。

### 5.7 公开预约入口

公开预约入口只用于外部提交申请。

必填字段：

- 姓名 / 法名。
- 性别。
- 手机号。
- 身份证号。
- 预计到寺日期。
- 预计离寺日期。
- 身份类型：居士、义工、学员、客人、其他。
- 是否用斋：早斋、午斋、药石。

建议选填字段：

- 紧急联系人。
- 紧急联系人电话。
- 参与营期 / 法会。
- 班级 / 分组。
- 房间偏好：男寮、女寮、不限、需协助。
- 备注。

不允许公开填写或展示：

- 押金、房费、退款。
- 床位编号。
- 管理员备注。
- 黑名单 / 风险标记。
- 操作人。
- 后台住客、房态、报表数据。

公开预约提交后进入后台预约池，状态为 `预约` 或 `待确认`，由内部人员审核。

### 5.8 房务

房务流转：

- 退房后标记脏房。
- 脏房 → 净房 → 查房 → 可入住。
- 维修床不可分配。
- 备用床不参与正式统计和自动分配。

### 5.9 报表

报表至少包括：

- 厨房用斋汇总。
- 日报。
- 月报。
- 营期统计。
- 历史挂单查询。
- CSV 导出。

### 5.10 备份与迁移

本地模式：

- 导出 `ketang.db`。
- 从 `ketang.db` 恢复。

在线模式：

- 管理员 JSON 导出。
- 管理员 JSON 导入。
- Cloudflare D1 数据库级备份。
- 后续 D1 定时备份到 R2。

本地旧数据需要迁移到云端，迁移后 D1 成为正式权威数据源。

## 6. 在线多人要求

- 多人同时访问同一份 D1 数据。
- 关键写操作必须走后端业务 API。
- 床位并发冲突必须由数据库约束和后端逻辑拦截。
- 普通知客师不能直接管理用户表。
- 操作留审计日志。
- 房态看板需要自动刷新或提示刷新。

关键写操作包括：

- 入住。
- 退房。
- 换床。
- 续住。
- 预约转入住 / 分床。
- 删除挂单。
- 保存用斋。
- 房务状态更新。
- 营期批量取消 / No-show。

## 7. 明确不做

- 全寺 ERP。
- OA 审批。
- 完整会计系统。
- 多租户 SaaS。
- 外部用户后台注册。
- App Store / 微软商店上架。
- Electron / Tauri 安装包。
- 与客堂住宿无关的大型模块。
